# Independent review of the GLM FA2 diagnostic

Review scope: the local generator, captured vendor baseline and emitted diagnostic; no GPU execution, model requests or remote mutations. The baseline source is pinned to SHA256 `7a19dafb16f1a2f9ac58992ce78e4d27b8f52edf08059c387d4f32d70d0edab3`, from vendor vLLM `0.1.dev20051+g487ecf187` after the existing SM120 port.

Final verdict: cleared for the dedicated eager diagnostic, with marker activation only after startup finishes. The reviewed output is `analysis/glm_fa2_diagnostic/flashinfer_mla_sparse_sm90.py`, SHA256 `e7f158bf314a49d14f95301b36c7d7b9e8d65b315def1cdb50e6feb034970c73`; its adjacent manifest matches the bytes and current generator. This clears the instrumentation for testing. It establishes no GPU correctness, quality recovery or throughput result.

The initial review found the following gaps. They are now corrected and covered by the tests described below.

1. **Current rows must be authoritative.** The original hook trusts the previous host plan's `_glm_audit_active_rows` and treats all later rows as padding. That can hide an undersized stale plan. The current metadata includes `num_actual_tokens`, `num_reqs` and `query_start_loc`; those must agree with each other and the plan. The available query and converted-slot rows must also be checked. In mixed prefill/decode dispatch, `forward_mqa` can receive only a decode prefix; a plan covering more rows than that callback supplies must fail visibly rather than become presumed padding. [Pinned metadata definition](https://github.com/vllm-project/vllm/blob/487ecf187/vllm/v1/attention/backends/mla/flashinfer_mla_sparse.py), [MLA dispatch](https://github.com/vllm-project/vllm/blob/487ecf187/vllm/model_executor/layers/attention/mla_attention.py).
2. **Validate request indexing before conversion.** The converter checks a selected token's block-column range, but it uses `req_id` to address the block table without a request-row guard. Checking request IDs only after conversion is too late to prevent that read. Query metadata and request-row bounds belong before the converter call. [Pinned converter](https://github.com/vllm-project/vllm/blob/487ecf187/vllm/v1/attention/backends/mla/sparse_utils.py).
3. **Validate the physical cache range and live-zero case.** A nonnegative converted slot can still exceed the actual cache allocation. Pass the real cache/query tensors to the hook and bound each live prefix slot by the cache's physical slot count. Reject unsupported dtypes/ranks before narrowing counts, and reject an all-masked live query even when its planned count also equals zero. Zero-query padding remains inert.

The existing compact-prefix check has the correct underlying contract: `return_valid_counts=True` initializes output to `-1`, compacts valid slots into `[0, count)`, and leaves the tail negative. Prefix order is unspecified and must remain unchanged. The diagnostic observes that contract before the baseline's slot-zero clamp. [Converter capture](glm_fa2_primary_sources_20260905.json).

The exact-count replan uses the original `state.plan` and preserves fixed-width row offsets, one query per live row, head geometry, softmax scale, BF16 query type, KV dtype and selected indices. FlashInfer's plan consumes host lengths when constructing its schedule, so supplying only corrected live lengths is meaningful after all row and capacity checks pass. Its `use_cuda_graph=True` wrapper option retains fixed buffers; it does not itself put the instrumented call inside a CUDA graph. Engine `--enforce-eager` and the callback's stream-capture guard are both required. [FlashInfer 0.6.18 planner](https://github.com/flashinfer-ai/flashinfer/blob/v0.6.18/flashinfer/mla/_core.py).

With no marker configured, the original emitted module changes no attention math: it adds imports, a saved host-row-count attribute and an early-returning hook. Configuring a marker path intentionally requires eager mode at initialization even while the file is absent. The marker must be created after startup profiling; setting it during profiling would audit dummy inputs. Exact mode remains a diagnostic that synchronizes to the CPU and replans; its timing cannot be compared with production throughput.

The final source also validates live request IDs against the request implied by `query_start_loc`, and checks referenced physical block values before their int32 multiplication. The latter prevents a corrupt large block ID from wrapping into an apparently valid converted slot. Bounded 128-query chunks keep validation scratch memory limited; conservative int32 element-count guards cover converter row-address products. These observations do not change query values, sparse selections or their order.

One important converter detail required a further correction: its block-table load mask tests the computed block column, independently of the later negative-token output mask. Triton integer division truncates toward zero, so `-1` through `-(block_size - 1)` produce column zero and can read a block table even though their final output is a sentinel. The final audit uses truncating division and validates request-row bounds for every actual converter read, including padding. Physical block-value bounds apply only to nonnegative selected lanes on live rows, because converted values on zero-query padding never enter attention. A second independent source review confirmed this matches the pinned DCP=1, no-prefill-workspace converter path. [Triton integer semantics](https://triton-lang.org/main/python-api/triton-semantics.html).

All 30 tests pass with real CPU Torch `2.8.0+cpu`, including runtime checks for stale batch/owner metadata, negative-sentinel block-table reads, inert padding, wrapped physical block IDs, malformed compact prefixes, live-zero counts and exact replanning. Additional independent callback checks covered shape/dtype/geometry mismatches and the FP8 uint8 cache contract. A direct exercise of the captured original `state.plan` confirmed that exact replanning preserves query and sparse-row offsets, padded lengths, head geometry, scale and dtypes; the hook leaves supplied slots, counts and index storage unchanged. Marker-absent no-op and configured-marker graph rejection were also checked. These CPU checks do not execute FlashInfer or prove GPU behavior.

Final byte verification confirms the emitted source equals the current generator output. Fifteen of 18 original methods retain identical ASTs; only state initialization, host planning and `forward_mqa` contain inserted instrumentation. The older copy under `report/` belongs to the benchmarking session and was not overwritten. Subsequent experimental edits move to the `codex/priority-models` worktree.
